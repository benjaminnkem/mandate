Generated by the final Prompt 15 audit pass. Read `AGENTS.md` first if you have not; it is the operating contract
this handoff assumes. This document is written so another engineer can pick up the project from a clean machine.

**Status at handoff: the product is built and gated (security review passed, full test suite green, reproducible

## 1. Architecture actually built

Everything in `docs/PRD.md`'s v1 scope lock exists and passes its own test suite:

- **On-chain program** (`programs/mandate`, Anchor 1.2.0): 23 instructions — protocol config with two-step admin
  transfer and new-risk pause; immutable versioned observer sets; an approved-market registry keyed by exact DLMM
  pool address; sponsor-created mandates with atomic USDC escrow into a program-owned vault; open provider
  bidding with nonces; sponsor award with exact per-epoch reward splitting (remainder to the final epoch); a
  provider-registered, bounded position set that locks before the mandate starts; permissionless activation;
  per-observer epoch attestation bound to mandate + epoch + observer + position set + algorithm version;
  threshold quorum finalization that recomputes compliance on-chain from attested integers (never trusting an
  observer's own verdict); an explicit `Unavailable` outcome for epochs no valid quorum could measure in time;
  provider reward claims; sponsor surplus/refund withdrawal; mandate closing. `crates/mandate-core` holds every
  checked-integer settlement/accounting/compliance/timing calculation as pure, unit-tested Rust the program calls
  into — no arithmetic in an instruction handler itself decides money.
- **Measurement engine** (`packages/meteora`): a deterministic, versioned algorithm that reproduces real
  PreStocks/USDC Meteora DLMM measurements byte-for-byte from a recorded mainnet snapshot, using the official
  `@meteora-ag/dlmm` SDK (never hand-rolled bin/quote math). Produces a canonical, hashable evidence bundle.
- **Observer** (`apps/observer`): one key per process, leader/replay protocol (ADR 0015) — one observer measures
  live chain state and publishes the exact snapshot; the others replay it and sign only if their own computation
  reproduces the leader's hash exactly. Durable evidence is written *before* an attestation is submitted, and
  every retry path checks on-chain/local state first so a crash never double-submits or silently swallows a
  result.
- **Read plane** (`apps/indexer`, `apps/scheduler`, `apps/api`, `packages/db`): an account-authoritative indexer
  with a durable cursor and a from-chain rebuild command; an idempotent job queue and scheduler (permissionless
  finalize jobs, optional low-balance relayer); a typed read API with unsigned-transaction-builder endpoints
  (never a signer); Prometheus metrics and alert rules.
- **Web application** (`apps/web`): a direct Wallet Standard integration (no legacy adapter registry, no private
  key ever touches it); every required surface (landing, approved markets, explore mandates, create-mandate
  wizard, mandate detail, provider workspace, methodology, evidence inspector); one shared financial-write
  component that never claims success before chain confirmation.
- **Prompt 13 rehearsal tooling** (`scripts/src/surfpool-e2e.ts`): the administrative/lifecycle CLI used to prove
  the whole product end-to-end against a Surfpool mainnet fork — see `docs/runbooks/surfpool-e2e.md` for the full
  transcript with real transaction signatures.

Repository layout matches `docs/ENGINEERING_STANDARDS.md` §2 exactly; see that file for the tree.

## 5. How to create and secure observer keys

Full detail in `docs/runbooks/observer-keys.md`. Summary:

```bash
pnpm observers:provision   # writes .keys/observer-1..3.json (mode 0600, gitignored), prints public keys
```

Three separate keypairs, three separate OS processes — never one process holding two identities. Each observer
refuses to start unless it derives `OBSERVER_EXPECTED_PUBKEY` from its own key file, and refuses if the key file
is readable by other users. The program itself rejects an observer set that contains the protocol admin key. Fund
each with a little SOL (attestation rent is about 0.0025 SOL per attestation, plus fees). In production, diversify
RPC providers and, ideally, operators across the three keys — two colluding observers can still attest false
metrics; the design makes disagreement visible, not collusion-proof (documented v1 trust assumption, ADR 0004 /
`docs/EDGE_CASES_AND_OPEN_DECISIONS.md` §6).

Create the on-chain set from the three printed public keys with `create_observer_set` (threshold 2), immutable
once created; a lost/rotated key requires a *new* version, bound only by future mandates.

## 6. Database and Redis setup

- **Postgres**: schema and migrations live in code at `packages/db/src/migrations.ts` (no loose `.sql` files),
  applied with:
  ```bash
  DATABASE_URL=<url> pnpm db:migrate
  ```
  Postgres is a **projection**, never settlement authority — every table can be dropped and rebuilt from chain
  alone (§8 below). Recommended production setup: automated backups, point-in-time recovery, TLS, least-privilege
  service users, a separate migration-runner role.
- **Redis**: used by `apps/scheduler`'s job queue (idempotent, deduplicated by a stable `key`, leased with
  `FOR UPDATE SKIP LOCKED` so two workers never double-process the same job). Configure persistence appropriate
  for job durability, auth/TLS, and a distinct namespace per environment.
- **Tests never touch a real database by default** — `createTestDb()` boots an in-process PGlite engine per test
  unless `TEST_DATABASE_URL` is set, in which case it creates and drops a real throwaway Postgres database per
  test run.

## 8. Rebuilding the database from chain

```bash
DATABASE_URL=<url> pnpm indexer:rebuild
```

Destructive to derived tables only (never to chain state, which remains authoritative). **Verified in this
session**: killed the indexer mid-run, generated a real on-chain transaction while it was down, restarted it —
it resumed from its durable `chain_cursor` row and synced exactly the one new transaction, no duplication or
loss. Then ran a full destructive rebuild against the same live chain and confirmed the reconstructed read model
(`mandates`, `epoch_results`, `earned_raw`/`claimed_raw` amounts) matched the pre-rebuild state exactly. Full
transcript in `docs/runbooks/surfpool-e2e.md`.

## 12. Known limitations

- **No real mainnet or devnet deployment yet.** Everything proven end-to-end so far is Surfpool-fork or local.
- **Reproducible-build third-party verification (`solana-verify build`) currently cannot complete** against
  Anchor 1.2.0, for the external, root-caused reason in §3. Local determinism is confirmed by hash comparison
  across a clean rebuild instead.
- **S3-compatible evidence storage is schema-only**, not implemented; only `filesystem` mode works today.
- **The scheduler's automatic job planning is anchored to real wall-clock time**, not the chain's own clock. This
  is correct for production, but means a rehearsal that uses `surfnet_timeTravel` to fast-forward the fork's
  on-chain clock (as Prompt 13 did) cannot exercise the scheduler's own automatic finalize/retry path live in the
  same session — confirmed and documented in `docs/runbooks/surfpool-e2e.md`. The underlying queue retry/lease
  mechanics are unit-tested directly in `packages/db/test/queue.test.ts`, independent of this timing conflict.
- **A provider can register one throwaway, unverified position pubkey** (register_positions does not check
  ownership — that is deliberately deferred to observers, per architecture) and permanently block the sponsor's
  *fast* refund path (`refund_unactivated_mandate`), forcing the sponsor to wait out the full mandate schedule
  before recovering funds via the normal non-compliant/unavailable path. This is a documented, tested, deliberate
  v1 design decision (ADR 0014) with a hard upper bound (the protocol's configured `max_duration_seconds`, capped
  at 30 days) — flagged here so the product owner can re-confirm the bound is acceptable at production scale,
  not because it is a bug.
- **`submit_attestation` accepts an observation timestamped anywhere inside an epoch's window**, not only near
  its end. This matches the documented single-snapshot measurement design (`docs/TECHNICAL_SPEC.md`) but is worth
  the product owner's awareness alongside the already-documented "just-in-time liquidity" gaming limitation in
  `docs/TEST_SECURITY_RUNBOOK.md` §7.
- **Dependency audit**: `pnpm audit --prod` found one real, currently-unpatched HIGH advisory in production code
  paths — `bigint-buffer` (buffer overflow in `toBigIntLE()`), pulled in transitively via
  `@solana/spl-token → @solana/buffer-layout-utils`. This is a well-known, ecosystem-wide unpatched issue in the
  Solana JS toolchain with no upstream fix available at audit time; track upstream `@solana/web3.js`/
  `@solana/spl-token` releases that drop it. Two more HIGH advisories (`toml`, via `@anchor-lang/core`, parsing
  only local trusted config; `nanoid`, build-time only via Next.js's PostCSS step) and two MODERATE (`uuid`,
  `stream-json`, via `@solana/web3.js`'s RPC HTTP client, exercised only against the operator's own trusted RPC
  endpoint) were found with low practical exploitability in this codebase's actual usage. `cargo audit` found
  zero vulnerabilities — only five "unmaintained crate" warnings, all transitive dependencies of the
  Solana/Anchor SDKs themselves (`ansi_term`, `bincode`, `derivative`, `libsecp256k1`, `paste`), not exploitable
  advisories.
- **Sponsor-integration bounty work (Clawpump, Prompt 14) was not attempted** — explicitly deferred pending a
  fresh, explicit product-owner decision, per its own gating text.

## 13. Admin/upgrade authority ownership and rotation plan

At handoff, the program's deploy/upgrade keypair is this development environment's own local key
(`~/.config/solana/id.json`), used only for the Surfpool rehearsal — it has never signed a devnet or mainnet-beta
transaction. Before any real deployment:

1. Generate (or designate) the real deploy/upgrade authority keypair; keep it offline/hardware-protected, never
   mounted in any API/indexer/observer container.
2. Move it to a multisig/timelock before meaningful funds are at risk, or explicitly document why not yet.
3. The protocol-admin authority (separate from upgrade authority — see `initialize_protocol`'s `terms.admin`) is
   scoped to: new protocol bounds, new `ObserverSet` versions, market enable/disable for *future* mandates, and
   new-risk pause. It has no reward-vault withdrawal authority anywhere in the program (confirmed by the security
   audit, §14).
4. The scheduler's optional relayer key is fee-payer only and holds no protocol authority — confirmed by direct
   source inspection (`apps/scheduler/src/chain.ts`).

## 14. Security review summary

Full pre-mainnet security review completed per `docs/TEST_SECURITY_RUNBOOK.md` §15, split across the on-chain
program and the off-chain backend/observer/web surfaces.

**On-chain program (`programs/mandate` + `crates/mandate-core`)** — no fund-loss or fund-seizure bug found. Every
settlement-critical arithmetic path runs through checked helpers; every PDA is canonically derived or, in
`finalize_epoch`'s `remaining_accounts` loop, manually re-derived and bump-checked; the accounting invariants
(`earned + forfeited <= accepted <= max`, `claimed <= earned`, vault balance == predicted balance) are asserted
after every state-changing instruction that touches them; observer-quorum replay/duplication/cross-epoch binding
is enforced; no admin instruction can reach the vault. Three items were flagged and handled:
- A generic-error-collapse gap (`InvariantViolation`, `EpochAlreadyFinalized`, `DivisionByZero` all fell through
  to a catch-all `Unexpected` code) was **fixed** — see the commit history for `programs/mandate/src/error.rs`.
- Two documented, deliberate design points (the position-registration griefing bound, and early-in-epoch
  attestation timing) are noted above in §12 for the product owner's awareness, not treated as bugs.

**Backend/observer/web** — clean. No human user private key anywhere in the codebase; the program's own
`token::authority` constraints (not the API) are what actually prevent claim/withdraw fund redirection, so this
holds even if the API were bypassed entirely; the job queue and observer attestation retry paths are both
crash-safe (checked directly in source, and separately demonstrated live in the Surfpool rehearsal); no SSRF
surface (every external fetch target is either hardcoded or method-allowlisted); no secret ever committed to git
history (checked exhaustively); rate limiting and zod input validation present on every API route. One defensive
fix applied: the structured logger's redaction list now also covers the Solana RPC URL env vars, since a paid
provider URL commonly embeds an API key.

Dependency and secret-scan findings are in §12. `cargo audit` and `pnpm audit --prod` were both run to completion.
