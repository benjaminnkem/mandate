# ADR 0009: Domain accounting model, validation rules and golden vectors

- Status: accepted
- Date: 2026-09-20

## Decisions

**Two implementations, one independent oracle.** `packages/domain` (TypeScript, `bigint` only) and `crates/mandate-core` (Rust, checked arithmetic, no `unwrap`/`panic`/unchecked ops enforced by workspace lints) implement identical semantics. Both are verified against `packages/domain/vectors/golden.json`, generated by `generate_golden.py`, a third implementation in Python with arbitrary-precision integers that shares no code with either. `python3 generate_golden.py --check` fails CI if the file is stale. Mutation checks confirm the vectors detect wrong comparison operators, remainder placement, and a mis-gated sponsor withdrawal.

**Accounting derives from invariants.** State is a handful of counters; everything else is computed (spec section 10). One field was added to the spec's suggested `Mandate`: `forfeited_reward_raw`, because the final epoch carries the remainder, so unresolved reward cannot be derived from epoch counts alone.

**Sponsor release timing (literal spec 6.15).** The sponsor may withdraw the award surplus (`max - accepted`) at any time after award, and forfeited rewards (`accepted - earned`) only after all epochs are resolved. Releasing a non-compliant epoch's reward immediately would be safe but is a different reading of the spec, so it was not adopted.

**Reward must cover the schedule.** Creation requires `max_reward >= total_epochs`, and a bid requires `requested_reward >= total_epochs`, so every compliant epoch earns at least one raw unit (recommendation in TEST_SECURITY_RUNBOOK section 2). The split function itself stays total: it accepts `R < N` and returns `base = 0`.

**Timing windows.** Epoch `i` covers `[start + i*E, start + (i+1)*E)`. An epoch is finalizable when the clock reaches its exclusive end; unavailable finalization is allowed at `end + unavailable_recovery_seconds`. To stop a sponsor from awarding so late that the provider cannot set up, creation requires `bidding_ends_at < start_at - position_lock_buffer_seconds - min_setup_window_seconds`, and the sponsor must accept by the start of that setup window. This adds three protocol parameters (`min_start_lead_seconds`, `position_lock_buffer_seconds`, `min_setup_window_seconds`) and two probe bounds to `ProtocolConfig`.

**Finalization is not idempotent on counters.** Counters cannot say which epoch indexes are done, so `finalize_epoch` takes an `already_finalized` flag from the caller. The program supplies it from the epoch result account's existence (Prompt 9).

## Not decided here

Which instant inside an epoch is the designated observation point is deferred to Prompt 8, where it becomes part of the versioned algorithm semantics. Admissible attestation times are already bounded by the epoch window.
